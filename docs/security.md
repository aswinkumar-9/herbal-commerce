# Security

Status: **living document.** Last reviewed on 2026-11-06, at the end of part 5 (inventory).

Security reference: OWASP ASVS 5.0, Level 2 (`docs/requirements.md`). The decisions behind this page are in ADR 0007 (customer authentication), ADR 0008 (security baseline), ADR 0009 (rate limiting), ADR 0010 (password recovery), ADR 0011 (data retention), ADR 0012 (Super Users and the audit log), ADR 0013 (staff MFA), ADR 0014 (staff sign-in), ADR 0015 (staff roles and Admin invitations), ADR 0016 (managing Admins), ADR 0017 (the audit log view and staff sign-ins), ADR 0018 (the customer's name, password and sessions), ADR 0019 (delivery addresses), ADR 0020 (product categories), ADR 0021 (products), ADR 0022 (pack sizes and prices), ADR 0023 (product images) and ADR 0024 (inventory). This page records the status of each control and the rules for features that do not exist yet.

## 1. Threat model in short

| | |
|---|---|
| What we protect | Customer accounts and personal data (today: name, email, password hash, delivery addresses and their phone numbers; later: orders, invoices), staff accounts, the catalog customers see, prices and stock, payment status |
| Who might attack | Anonymous internet users (password guessing, account enumeration, bots, overload), a customer trying to read another customer's data, someone holding a stolen token or phone, a compromised dependency, and our own mistakes (secrets in Git, development settings in production) |
| Exposure today | The API listens on `127.0.0.1` only and has no real users. The gaps in section 6 must be closed before that changes. |

## 2. Secure-by-design principles

| Principle | How it shows up |
|---|---|
| Deny by default | One global guard protects every endpoint. Only handlers marked `@Public()` are open. Protected routes take customer tokens unless marked `@StaffOnly()`, and routes marked `@SuperUserOnly()` refuse Admins. |
| Never trust the client | The server sets roles and, later, prices. The user ID comes from the token and the role from the database, never from the request. |
| Least privilege | Admin and Super User are separate roles, checked on every request. Super Users can only be created by a developer command, at most 3. Nobody but the Admin ever knows an Admin's password. The database gets a data-only runtime role before production. |
| Defense in depth | Refresh tokens are stored hashed and rotate on every use, and reusing one revokes the session. The session is also checked on every request. |
| Fail closed | The API refuses to start with invalid, missing or (in production) placeholder configuration. |
| Small attack surface | The API accepts JSON only and stays on localhost until it is deployed behind HTTPS. |
| Refuse cheaply | Rate limits run before any token check, database query or password hash, so a flood costs us as little as possible. |
| Privacy by design | No emails, passwords or tokens in logs, and only the data we need is stored. |

## 4. Control-by-control status

### 4.1 Input and injection

| Control | Status | Today | Rule or next action |
|---|---|---|---|
| SQL injection | Done | All queries go through Prisma, which sends values as parameters. Raw SQL appears eight times: a constant `SELECT 1` in `health/health.service.ts`, and seven row locks, in `addresses/addresses.service.ts`, `catalog/categories.service.ts`, `catalog/products.service.ts`, `catalog/variants.service.ts`, two in `catalog/images.service.ts` (the product, and the image), and one in `inventory/stock.service.ts` (the batch). The locks are tagged templates whose ID travels as a parameter (ADR 0019 to ADR 0024). zod checks every JSON request body, so no objects can be smuggled into queries. | Never use `$queryRawUnsafe`. Allowlist sort and filter fields. Check that IDs are valid UUIDs before querying (an invalid one would cause a 500): every route with an ID in its path uses `ParseUUIDPipe` (Admins since part 3B-5, ADR 0016; addresses, categories, products, pack sizes, images and stock batches too). |
| XSS | Done (API) | Responses are JSON only, apart from the image files, which are always WebP made by the API. helmet sends `nosniff` and a Content Security Policy. Emails escape the user's name and the link (`mail/mail.service.ts`). SVG uploads are refused (ADR 0023). | Website and admin console: a Content Security Policy, no raw HTML for product text, and image descriptions (`altText`) shown as text. |
| CSRF | Done (API) | Tokens travel in the `Authorization` header, which a browser never sends on its own. The API accepts JSON bodies only, and on the upload route image bodies, neither of which an HTML form on another website can send (ADR 0008, ADR 0023). | Website: keep the refresh token in a cookie with `HttpOnly; Secure; SameSite=Strict; Path=/v1/auth`, and add an `Origin` check or a CSRF token on the cookie endpoints. |
| File upload validation | Done (part 4D) | Product images only, by staff only (ADR 0023):<br>• the body is read only for a valid staff token, so anyone else's upload is never even read;<br>• at most 10 MB, not compressed, at most 6 images per product, and 120 uploads per hour per IP;<br>• the first bytes (magic bytes) must match the `Content-Type`, and only JPEG, PNG and WebP reach the image library. SVG, GIF and every other type are refused;<br>• the size is read from the header before decoding: at most 50 megapixels (decompression bombs), at least 400 pixels a side;<br>• every image is re-encoded to WebP from its pixels alone, so metadata (such as a GPS location) and anything hidden in the file are dropped. The uploaded file is never stored;<br>• the files get random names (a UUID), and `MediaStorage` accepts no other names, so no path can leave its folder;<br>• at most 2 images are processed at once, 10 wait, and the rest get `503`.<br>`multer` is still unused: the upload is a raw body, not a form. | The stored files are public by address, as product photos should be. If private files are ever needed (invoices, for example), they get private storage and signed, short-lived addresses. |
| SSRF | Not applicable yet | Nothing fetches a URL taken from user input. Email links use `WEB_BASE_URL` from the environment, never the request's `Host` header. | Payments and courier: call fixed hosts only. If a user-supplied URL ever has to be fetched: allowlist the hosts, block private IP ranges, disallow redirects, set timeouts. |

### 4.2 Authentication and authorization

| Control | Status | Today | Rule or next action |
|---|---|---|---|
| BOLA (broken object level authorization) | Done for what exists | `/v1/me` takes the user ID from the token, never from the request. The Admin routes, for Super Users only, act on Admins alone: any other ID, a Super User's included, gets `404` (ADR 0016). Delivery addresses, the first objects a customer reaches by ID, are always queried with `where: { id, userId }` or `where: { userId }`, so another customer's address answers `404` like an unknown one. The smoke test proves it on every run with a second customer (ADR 0019). | Orders and invoices: the same rule, `where: { id, userId: currentUser.id }` and `404` for other users' objects, with a test in which user B cannot reach user A's data. |
| Rate limiting and brute-force protection | Done (part 3D) | A global guard limits every route per IP (a 600 per minute baseline) and each sign-up and sign-in endpoint further. Login has three failure counters (email + IP, email, IP) that block for 15 to 60 minutes, are checked before any password work, and count unknown emails too. Counters live in Valkey with an in-memory fallback, keyed by HMAC so Valkey holds no emails or IPs. The client IP comes from `req.ip`, and only proxies listed in `TRUST_PROXY` may report it (ADR 0009). The staff login shares the three failure counters (a wrong code counts like a wrong password) and has its own limit of 10 attempts per minute per IP (ADR 0014). Inviting Admins and accepting invitations are limited to 20 per hour per IP each (ADR 0015). Changing the password while signed in is limited to 10 per hour per IP, and every wrong current password counts against the three failure counters too, so a stolen access token gives no faster way to guess the password (ADR 0018). | Tune the numbers with real traffic (429s are in the request logs). List the proxy in `TRUST_PROXY` when one exists. CAPTCHA in front of login only if real attacks appear. |
| Secure password storage | Done | argon2id with the OWASP minimum settings (19 MiB, 2 passes, 1 lane), 10 to 128 characters, no forced character rules (`auth/password.service.ts`). | Later: a breached-password check, a decision on Unicode normalization before real users, and rehashing when the hash settings change. |
| Account enumeration | Done | Registration, resend and forgot-password always give the same answer. Forgot-password does its lookup and sends its email after the response, so it is equally fast for every address. Login gives the same 401 for an unknown email, a wrong password and an unverified email, and runs a dummy hash for unknown emails. Response times are similar, not identical. The rate limits count unknown emails exactly like real ones, so a 429 reveals nothing either. The staff login gives one `401` for every failure, a disabled account included, so it never confirms a guessed password (ADR 0014). Accepting an Admin invitation gives one `400` for every refused link. Inviting an Admin answers `409` for an email that has an account, which only a signed-in Super User can ask, at most 20 times an hour (ADR 0015). | Every new endpoint that takes an email must follow the same rule. Endpoints for Super Users only may say that an email is taken, because they cannot work otherwise. |
| Session management | Done | Each customer login creates a 30-day session, and each staff login a 12-hour one (ADR 0014). Access tokens last 15 minutes. Refresh tokens rotate on every use, and reusing one revokes the session. Logout revokes the session. A password reset revokes every session of the account, and so does disabling an Admin, so enabling them later brings no old session back (ADR 0016). The session is checked on every request, so all of this takes effect at once. Ended sessions are deleted after 30 days (ADR 0007, ADR 0010, ADR 0011). | "Sign out everywhere" is done (`DELETE /v1/me/sessions`, ADR 0018), and so is changing the password while signed in, which ends every session too. Later: a list of active sessions, with "sign out this one". |
| Password recovery | Done (part 3A-4) | Reset links are 32 random bytes, stored only as a SHA-256 hash in their own table, valid for 30 minutes and once. They go only to active customers. The link is checked before any hashing, and every refused link gets the same 400. A reset sets the new password, marks the email verified, ends every session, lifts the login blocks for the owner and sends a "password changed" notice without a link (ADR 0010). | Staff reset (staff part). The website must post the token from the URL straight away and keep it out of its logs. A password change while signed in (part 3C-1) needs the current password, ends every session, cancels any waiting reset link and sends the same notice (ADR 0018). |
| Admin invitations | Done (part 3B-4) | Only a Super User can invite (`@SuperUserOnly()`). The Admin's account starts with a random password nobody knows. The invitation link works the same way as a reset link: 32 random bytes, stored only as a SHA-256 hash in its own table (`staff_invitations`), valid for 72 hours and once, claimed atomically, and checked before any hashing. Every refused link gets the same `400`. Accepting sets the Admin's own password (16 to 128 characters), marks the email verified, ends any sessions, and is audited with the Admin as the actor. The Super User never sees the token or the link. The Admin still cannot sign in until a developer sets up their MFA (ADR 0015). Since part 3B-5, a Super User can send a pending Admin a new link, and every older link then stops working, or remove the pending Admin (ADR 0016). | The admin console must post the token from the URL straight away and keep it out of its logs. |
| Managing Admins | Done (part 3B-5) | Super Users only (`@SuperUserOnly()`), and only Admin accounts: a Super User's ID gets `404`. Path IDs must be UUIDs (`400`). Disabling ends every session of the Admin at once. Only a disabled or pending Admin can be removed, so an active one must be disabled first (`409`). Each rule is part of the database write itself, so two requests at the same moment cannot both change something. Every change is audited in the same transaction, a removal with a snapshot of who it was. The list never contains the password hash or the MFA secret (ADR 0016). | Once orders or shipments record which Admin handled them, decide whether removing must become "disable for good". A second approver for destructive actions (ADR 0004) is still open. |
| MFA | Done for staff (parts 3B-2 and 3B-3) | Staff MFA (ADR 0013):<br>• TOTP from authenticator apps, our own implementation proven against the RFC test vectors;<br>• ±30 seconds of clock drift allowed;<br>• no code works twice (atomic);<br>• secrets encrypted with AES-256-GCM, bound to the user, under a separate `MFA_ENCRYPTION_KEY`;<br>• set up only with `pnpm api:setup-staff-mfa`, which saves only after a valid code, ends all sessions and is audited.<br>Staff sign in only with the password and a current code together, checked in that order, with one answer for every failure (ADR 0014). A staff member without MFA cannot sign in at all. | Later: recovery codes (hashed), passkeys and a QR code in the admin console. Customers: password only for now (the owner's choice); optional MFA later. |
| Server-side permission enforcement | Done (customers and the two staff levels) | The server sets the role at registration and at an invitation, and zod drops unknown fields such as `role`. A global deny-by-default guard checks the token and the session on every request, and reads the user's current role from the database in the same query, never from the token. Customer routes take only `customer` tokens of active Customers. Routes marked `@StaffOnly()` take only `staff` tokens of active Admins and Super Users with MFA set up, and a token for the other audience is refused like a forged one (ADR 0014). Routes marked `@SuperUserOnly()` refuse Admins with `403`, through a global roles guard that fails closed (ADR 0015). Today these are all the Admin routes (inviting, listing, disabling and enabling, removing and inviting again, ADR 0016) and deleting a category, a product or a pack size. Admins create, change, activate and deactivate categories, products and pack sizes, and set prices, as the permission matrix proposes; only deleting is narrowed to Super Users, on that one handler (ADR 0020 to ADR 0022). The one exception, by the owner's choice: Admins delete product images too, because replacing a photo is everyday work, and the audit log records who deleted which (ADR 0023). Admins and Super Users alike receive stock, correct batches and change stock, as the matrix proposes ("adjust, view movements"). Nobody deletes stock: a mistake is put right with a correction, and a pack size or product that still holds stock cannot be deleted (ADR 0024). The matrix's approval of large price changes is not built: every price change is audited instead (ADR 0022). | With the admin console features: finer staff permissions from the permission matrix in `docs/requirements.md`, once the owner has confirmed it. `staff/staff-routes.spec.ts` lists exactly which staff controllers, and which category, product and pack-size handlers, are Super User only, and names the image exception in its own test, so a change to that list is always deliberate. |
| Row-level security (RLS) | Decision: not now | The app connects as the database user that Docker creates, which is a superuser and bypasses RLS anyway. | Before production: separate database roles for migrations and for the running app (data access only, no schema changes). Ownership checks in the app stay the main control. RLS is optional later for orders, addresses and invoices. |

### 4.5 Further controls for this stack

| Control | Status | Rule or next action |
|---|---|---|
| Security logging | Done (basic) | Every failed login and refresh is logged with a reason, never with the email. These are logged as warnings: a staff email on the customer login, a reused refresh token, a refresh token used on the other sign-in path, a blocked account, a login that goes over a failure limit, and every failed staff sign-in that involves a real account (wrong password, wrong code, disabled, no MFA, a customer email). An error while checking a staff code is logged as an error. The staff code is never logged. Refused reset links and completed resets are logged with a reason and the user ID, and so are refused and accepted Admin invitations. Status changes, removals and new invitations of Admins are logged with the user ID and the Super User's ID, and category, product, pack-size, image and stock changes with the category's, product's, pack's, image's or batch's ID and the staff member's ID (a stock change with its reason too). An image file that cannot be deleted is logged as a warning (`Image files not deleted`, with its key). An Admin who tries a Super-User-only route gets `403`. Super User creation, MFA setups, every change to Admins and every successful staff sign-in are written to the audit log (ADR 0017). Valkey outages are logged once. Later: alerts on those warnings. |
| Denial of service through password hashing | Done (part 3D) | At most 2 argon2 operations run at once and 50 wait in line. Beyond that the answer is `503 SERVER_BUSY` with `Retry-After`, so a burst cannot use up Node's 4 worker threads (ADR 0009). |
| Denial of service through uploads | Done (part 4D) | An upload is read only for a valid staff token, so nobody else can make the API hold a large body. Uploads are at most 10 MB and 120 per hour per IP. A file whose header claims more than 50 megapixels is refused before anything is decoded. At most 2 images are processed at once and 10 wait; beyond that, `503 SERVER_BUSY` (ADR 0023). On a laptop, `/media` is served before the rate-limit guard. A CDN takes over before production (section 6). |
| Email flooding | Done (part 3D) | Register, resend and forgot-password send email to the address in the request, so all three count against one limit of 5 emails per hour per address, for known and unknown addresses alike. Admin invitations are sent only by signed-in Super Users, at most 20 per hour per IP. A first invitation goes only once to each address, because a second one gets `409`. Inviting the same Admin again counts against the 5 emails per hour per address too (ADR 0016). |
| Pre-account takeover | Done (parts 3A-4 and 3A-5) | Someone registers an email address that is not theirs and waits for the real owner to verify it. A password reset by the real owner sets their password, marks the address verified and ends every session (ADR 0010). A sign-up still unverified after 7 days is deleted, which frees the address (ADR 0011). |
| Product compliance (India) | Partly (parts 4B to 5) | A product goes live only with its type, licence number, maker's name and address, its ingredients, and its HSN code and GST rate. Since part 4D, by the owner's choice rather than the law, it also needs at least one image (ADR 0023). The API checks the product as it will be saved, and a database check constraint refuses a live product without them, even after a bug. An FSSAI licence must be 14 digits, and the product page always shows the licence, the maker and the country of origin (ADR 0021). Each pack has its net quantity and its MRP, and the shop's price is never above the MRP: checked by the API on the pack as it will be saved, and by a database check constraint. The GST rate must be one of today's rates (0, 5, 18 and 40%, since GST 2.0), and a chartered accountant confirms the rate for each HSN code (ADR 0022). Since part 5, stock is kept per batch, with its batch number and dates as on the label; an expired batch is never received, and a batch is sold only with at least 6 months left (ADR 0024). Still to do: a lawyer's review of the label and price rules, and whether the product page must show a batch's expiry; recalls by batch number; GST on invoices (with orders). Curative claims in the descriptions are restricted by law and cannot be checked by code, so staff must review what they write. |
| Business logic (orders, payments) | Partly (stock, part 5) | Stock never goes below 0: a movement locks its batch, and a database check refuses a negative quantity even after a bug. Stock changes only through movements that are never changed or deleted, and a batch that holds stock is never deleted (ADR 0024). Later, with orders: the server calculates prices, tax and totals; orders and payments carry idempotency keys; stock reservations expire; coupons have limits; checks against cash-on-delivery abuse. |
| Audit log and Super User limit | Partly (parts 3B-1, 3B-4 to 3B-6, 4A to 4D, and 5) | Done for what exists (ADR 0012, ADR 0015, ADR 0016, ADR 0017, ADR 0020 to ADR 0024):<br>• `audit_log` is append-only: database triggers refuse `UPDATE`, `DELETE` and `TRUNCATE`;<br>• entries have no foreign keys, so they outlive what they describe;<br>• each entry is written in the same transaction as its change, with secret-looking fields redacted;<br>• audited: Super User creation, MFA setups, Admin invitations (`admin.invited`, `admin.invitation_resent`), accepted invitations (`admin.invite_accepted`), status changes (`admin.disabled`, `admin.enabled`) and removals (`admin.removed`, with a snapshot of who it was), every successful staff sign-in (`staff.signed_in`, in the same transaction as its session), and every category, product, pack-size and image change (`category.*`, `product.*`, `variant.*` and `image.*`: `created`, `updated` with only the changed fields, and `deleted` with a snapshot, each after a row lock so that `before` is exact). So every price change keeps the old and the new price, and a deleted product's entry keeps its packs and images. Since part 5, stock too: `batch.received`, `batch.updated` and `stock.changed`, with the quantity before and after and the reason. A refused change writes nothing;<br>• a request that changes nothing writes no entry;<br>• entries made through the API carry the checked actor, the client IP and the request ID (`@CurrentAuditContext()`);<br>• the limit of 3 Super Users is enforced by the app and by a database trigger with a lock.<br>• failed sign-ins stay out, because anyone can cause them and the log can never be cleaned;<br>• Super Users read the log at `GET /v1/staff/audit-log`: newest first, paged by cursor, filtered by action, actor or target, with the accounts named in one query.<br>Still to do: a database role for the app that may only insert and read audit entries (before production), and a retention period for audit entries (DPDP Act). |
| Supply chain beyond npm | Later (before production) | Pin Docker images by digest and add secret scanning in CI (for example gitleaks). The AI-skill files in `apps/api/.agents` give instructions to AI tools, so review changes to them like code. |
| Privacy (India's DPDP Act) | Partly (part 3A-5) | Retention periods for sessions, tokens and unverified accounts are enforced by an hourly job inside the API (ADR 0011). Delivery addresses and their phone numbers (part 3C-2) are shown only to their owner, and go with the account when it is deleted (ADR 0019). Still to do: a list of the personal data held (now including addresses and phone numbers), a log retention period, deletion on request, consent, and a breach plan. Data stays in India. |
| Backups and email | Later (before production) | Encrypted backups with a rehearsed restore. SPF, DKIM and DMARC on the sending domain. |

## 6. Must be done before the API leaves localhost

Rate limiting, brute-force protection and the hashing cap were on this list and were done in part 3D. Still open:

1. HTTPS everywhere, so HSTS takes effect, and TLS to the database.
2. The reverse proxy or load balancer listed in `TRUST_PROXY`. Without it, every customer would share the proxy's IP in the rate limits.
3. Separate database roles for migrations and for the running app. The app's role may only insert and read `audit_log`, so not even a compromised API can rewrite history or drop the triggers.
4. Secrets in a secret manager, one set per environment.
5. `/health/ready` details hidden from the public.
6. A log retention period. (The cleanup of expired sessions and tokens has run since part 3A-5.)
7. `pnpm audit` clean, Dependabot alerts on, secret scanning in CI, Docker images pinned by digest.
8. Encrypted backups with a rehearsed restore.
9. Image files from object storage behind a CDN, over HTTPS, with `MEDIA_BASE_URL` pointing at it. On a laptop the API serves `/media` itself, before the rate-limit guard (ADR 0023).

## 7. Keeping this page current

- Change a control's status in the same pull request that changes the control.
- Before every pull request, run `pnpm api:typecheck`, `pnpm api:test`, `pnpm api:lint`, `pnpm api:build`, `pnpm audit` and `pnpm api:smoke`.
- Repeat the full review whenever a part adds attack surface: uploads, payments, the website, the mobile app, staff login, staff permissions.

## 8. Glossary

| Term | Meaning |
|---|---|
| ASVS | OWASP Application Security Verification Standard, the security checklist this project follows (Level 2). |
| argon2id | A slow, memory-hard password hashing algorithm recommended by OWASP. |
| BOLA | Broken object level authorization: reading or changing someone else's data by changing an ID in a request. |
| CGNAT | Carrier-grade NAT: a mobile or broadband provider puts many customers behind one public IP address. |
| CORP | Cross-Origin-Resource-Policy: a header that says which other websites may show a file, such as an image. helmet's default is "only this site"; `/media` allows every site. |
| CORS | Cross-origin resource sharing: the browser rules for which other websites may read the API's responses. |
| CSP | Content Security Policy: a header that tells the browser which scripts and resources a page may load. |
| CSRF | Cross-site request forgery: another website making the user's browser send a request that carries the user's cookies. |
| Decompression bomb | A small file that claims, or unpacks to, a huge image, made to fill the server's memory. Refused by reading the size from the header before decoding. |
| DPDP Act | India's Digital Personal Data Protection Act, 2023. |
| EXIF | Details a camera stores inside a photo, such as the date, the camera model and often the GPS location. Re-encoding drops them. |
| HKDF | A standard way to derive a separate key for one job from an existing secret. |
| HMAC | A signature made with a shared secret. Used to prove that a webhook really came from the payment gateway, and to hash rate-limit keys. |
| HSTS | A header that tells browsers to use HTTPS only. |
| JWT | JSON Web Token: the signed access token the app sends with each request. |
| Magic bytes | The fixed first bytes of a file format, such as `FF D8 FF` for JPEG. They say what a file really is, whatever its name or `Content-Type` claim. |
| MFA / TOTP | Multi-factor authentication. TOTP is the 6-digit code from an authenticator app. |
| RLS | Row-level security: PostgreSQL rules that limit which rows a database user can see. |
| SSRF | Server-side request forgery: tricking the server into fetching a URL the attacker chooses. |
| XSS | Cross-site scripting: getting the browser to run an attacker's script inside our website. |
