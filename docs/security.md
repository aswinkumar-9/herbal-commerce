# Security

Status: **living document.** Last reviewed on 2026-11-13, at the end of part 12B (the admin console's catalog pages).

Security reference: OWASP ASVS 5.0, Level 2 (`docs/requirements.md`). The decisions behind this page are in ADR 0007 (customer authentication), ADR 0008 (security baseline), ADR 0009 (rate limiting), ADR 0010 (password recovery), ADR 0011 (data retention), ADR 0012 (Super Users and the audit log), ADR 0013 (staff MFA), ADR 0014 (staff sign-in), ADR 0015 (staff roles and Admin invitations), ADR 0016 (managing Admins), ADR 0017 (the audit log view and staff sign-ins), ADR 0018 (the customer's name, password and sessions), ADR 0019 (delivery addresses), ADR 0020 (product categories), ADR 0021 (products), ADR 0022 (pack sizes and prices), ADR 0023 (product images), ADR 0024 (inventory), ADR 0025 (cart), ADR 0026 (checkout and orders), ADR 0027 (payments with Razorpay), ADR 0028 (staff order handling), ADR 0029 (order emails), ADR 0030 (search and filters) and ADR 0031 (the admin console). This page records the status of each control and the rules for features that do not exist yet.

## 1. Threat model in short

| | |
|---|---|
| What we protect | Customer accounts and personal data (today: name, email, password hash, delivery addresses and their phone numbers, orders and their payments; later: invoices), staff accounts, the catalog customers see, prices and stock, whether an order is paid, the money that goes back, and the Razorpay keys. Card and bank details never reach us: customers type them into Razorpay's page. |
| Who might attack | Anonymous internet users (password guessing, account enumeration, bots, overload), a customer trying to read another customer's data, someone holding a stolen token or phone, a compromised dependency, and our own mistakes (secrets in Git, development settings in production) |
| Exposure today | The API listens on `127.0.0.1` only and has no real users. The gaps in section 6 must be closed before that changes. The admin console runs only on a laptop, at `http://localhost:5173`. |

## 2. Secure-by-design principles

| Principle | How it shows up |
|---|---|
| Deny by default | One global guard protects every endpoint. Only handlers marked `@Public()` are open. Protected routes take customer tokens unless marked `@StaffOnly()`, and routes marked `@SuperUserOnly()` refuse Admins. |
| Never trust the client | The server sets roles and, later, prices. The user ID comes from the token and the role from the database, never from the request. |
| Least privilege | Admin and Super User are separate roles, checked on every request. Super Users can only be created by a developer command, at most 3. Nobody but the Admin ever knows an Admin's password. The database gets a data-only runtime role before production. |
| Defense in depth | Refresh tokens are stored hashed and rotate on every use, and reusing one revokes the session. The session is also checked on every request. |
| Fail closed | The API refuses to start with invalid, missing or (in production) placeholder configuration. |
| Small attack surface | The API accepts JSON only and stays on localhost until it is deployed behind HTTPS. |
| Refuse cheaply | Rate limits run before any token check, database query or password hash, so a flood costs us as little as possible. |
| Privacy by design | No emails, passwords, tokens or search words in logs, and only the data we need is stored. |

## 4. Control-by-control status

### 4.1 Input and injection

| Control | Status | Today | Rule or next action |
|---|---|---|---|
| SQL injection | Done | All queries go through Prisma, which sends values as parameters. Raw SQL appears fourteen times: a constant `SELECT 1` in `health/health.service.ts`, seven row locks, in `addresses/addresses.service.ts`, `catalog/categories.service.ts`, `catalog/products.service.ts`, `catalog/variants.service.ts`, two in `catalog/images.service.ts` (the product, and the image), and one in `inventory/stock.service.ts` (the batch, which orders lock too, several at once in the order of their IDs), and in `cart/cart.service.ts` the statement that makes or finds a customer's cart and locks it (`INSERT … ON CONFLICT … DO UPDATE`). Since part 11, the shop's search matches words with `pg_trgm` in `catalog/product-search.service.ts`: the words are a bound parameter in each of the six places they go, and a search for SQL finds nothing and changes nothing (ADR 0030). Since part 12B, three more row locks, when staff put categories or a category's products in a new order (every row, in the order of their IDs, and the category held), and the staff search by name in `catalog/products.service.ts`, whose words, category and status are bound parameters; a search for SQL finds nothing there either, checked on a real database (ADR 0032). Check that IDs are valid UUIDs before querying (an invalid one would cause a 500): every route with an ID in its path uses `ParseUUIDPipe` (Admins since part 3B-5, ADR 0016; addresses, categories, products, pack sizes, images, stock batches and orders too). |
| XSS | Done (API and admin console) | Responses are JSON only, apart from the image files, which are always WebP made by the API. helmet sends `nosniff` and a Content Security Policy. Emails escape the user's name and the link (`mail/mail.service.ts`). Since part 10, the order emails escape every value too, such as product names and the delivery address (ADR 0029). | CSRF | Done (API and admin console) | Tokens travel in the `Authorization` header, which a browser never sends on its own. The API accepts JSON bodies only, and on the upload route image bodies, neither of which an HTML form on another website can send (ADR 0008, ADR 0023). Since part 12A, the admin console's refresh token is in a cookie: `HttpOnly; SameSite=Strict; Path=/v1/staff/auth`, `Secure` over HTTPS. The API reads it only on the three staff auth routes, and only when `Origin` is exactly `ADMIN_ORIGIN`. | File upload validation | Done (part 4D) | Product images only, by staff only (ADR 0023):<br>• the body is read only for a valid staff token, so anyone else's upload is never even read;<br>• at most 10 MB, not compressed, at most 6 images per product, and 120 uploads per hour per IP;<br>• the first bytes (magic bytes) must match the `Content-Type`, and only JPEG, PNG and WebP reach the image library. SVG, GIF and every other type are refused;<br>• the size is read from the header before decoding: at most 50 megapixels (decompression bombs), at least 400 pixels a side;<br>• every image is re-encoded to WebP from its pixels alone, so metadata (such as a GPS location) and anything hidden in the file are dropped. If private files are ever needed (invoices, for example), they get private storage and signed, short-lived addresses. |
| IDs and filters from the address bar | Done (admin console, part 12B) | The console puts an ID into an API path only if it is a UUID: anything else is "There is no such product", and no request is sent, so `..`, `/` or `?` from the address bar can never reach the API's path (`src/catalog/catalog-api.ts`). Since part 8, the API calls one fixed host, `https://api.razorpay.com`, with a 10-second timeout. A Razorpay ID that goes into a path is first checked against Razorpay's form (`pay_…`, `order_…`), so it can't change the path (ADR 0027). | Courier: call fixed hosts only. If a user-supplied URL ever has to be fetched: allowlist the hosts, block private IP ranges, disallow redirects, set timeouts. |

### 4.2 Authentication and authorization

| Control | Status | Today | Rule or next action |
|---|---|---|---|
| BOLA (broken object level authorization) | Done for what exists | `/v1/me` takes the user ID from the token, never from the request. The Admin routes, for Super Users only, act on Admins alone: any other ID, a Super User's included, gets `404` (ADR 0016). Delivery addresses, the first objects a customer reaches by ID, are always queried with `where: { id, userId }` or `where: { userId }`, so another customer's address answers `404` like an unknown one. The smoke test proves it on every run with a second customer (ADR 0019). The cart has no ID at all: it is always the one of the customer in the token, and its lines are found through it. The smoke test proves that a second customer's cart stays empty (ADR 0025). Orders are always looked up with `where: { id, userId }` or `where: { userId }`, so another customer's order answers `404`, and the smoke test proves it with a second customer (ADR 0026). Paying for one too: starting or confirming a payment for another customer's order answers `404`, and a payment is checked against the Razorpay order saved for this order, so it can't be used for another (ADR 0027). Staff reach every order by its ID, as their work needs, but customers never reach the staff order routes (`401`, proved by the smoke test), and an Admin's view of an order leaves its payment out (ADR 0028). | Invoices and payments: the same rule, `where: { id, userId: currentUser.id }` and `404` for other users' objects, with a test in which user B cannot reach user A's data. |
| Rate limiting and brute-force protection | Done (part 3D) | A global guard limits every route per IP (a 600 per minute baseline) and each sign-up and sign-in endpoint further. Login has three failure counters (email + IP, email, IP) that block for 15 to 60 minutes, are checked before any password work, and count unknown emails too. Counters live in Valkey with an in-memory fallback, keyed by HMAC so Valkey holds no emails or IPs. The client IP comes from `req.ip`, and only proxies listed in `TRUST_PROXY` may report it (ADR 0009). The staff login shares the three failure counters (a wrong code counts like a wrong password) and has its own limit of 10 attempts per minute per IP (ADR 0014). Inviting Admins and accepting invitations are limited to 20 per hour per IP each (ADR 0015). Changing the password while signed in is limited to 10 per hour per IP, and every wrong current password counts against the three failure counters too, so a stolen access token gives no faster way to guess the password (ADR 0018). Placing an order is limited to 30 per hour per IP, since each order holds stock (ADR 0026). Starting and confirming payments, 60 an hour each per IP, since each may call Razorpay (ADR 0027). Searching, 120 a minute per IP, since each search weighs every live product (ADR 0030). | Tune the numbers with real traffic (429s are in the request logs). List the proxy in `TRUST_PROXY` when one exists. CAPTCHA in front of login only if real attacks appear. |
| Secure password storage | Done | argon2id with the OWASP minimum settings (19 MiB, 2 passes, 1 lane), 10 to 128 characters, no forced character rules (`auth/password.service.ts`). | Later: a breached-password check, a decision on Unicode normalization before real users, and rehashing when the hash settings change. |
| Account enumeration | Done | Registration, resend and forgot-password always give the same answer. Forgot-password does its lookup and sends its email after the response, so it is equally fast for every address. Login gives the same 401 for an unknown email, a wrong password and an unverified email, and runs a dummy hash for unknown emails. Response times are similar, not identical. The rate limits count unknown emails exactly like real ones, so a 429 reveals nothing either. The staff login gives one `401` for every failure, a disabled account included, so it never confirms a guessed password (ADR 0014). Accepting an Admin invitation gives one `400` for every refused link. Inviting an Admin answers `409` for an email that has an account, which only a signed-in Super User can ask, at most 20 times an hour (ADR 0015). | Every new endpoint that takes an email must follow the same rule. Endpoints for Super Users only may say that an email is taken, because they cannot work otherwise. |
| Session management | Done | Each customer login creates a 30-day session, and each staff login a 12-hour one (ADR 0014). Access tokens last 15 minutes. Refresh tokens rotate on every use, and reusing one revokes the session. Logout revokes the session. A password reset revokes every session of the account, and so does disabling an Admin, so enabling them later brings no old session back (ADR 0016). The session is checked on every request, so all of this takes effect at once. Ended sessions are deleted after 30 days (ADR 0007, ADR 0010, ADR 0011). Since part 12A, the admin console signs staff out after 30 minutes without activity in any of its tabs, by the owner's choice, and if the server can't be reached then, it locks anyway and ends the session at its next start. It renews one token at a time, across tabs too, so reuse detection never ends a session by mistake, and signing out in one tab signs out the others (ADR 0031). | "Sign out everywhere" is done (`DELETE /v1/me/sessions`, ADR 0018), and so is changing the password while signed in, which ends every session too. Later: a list of active sessions, with "sign out this one". An idle limit in the API itself, if the customer website needs one. |
| Password recovery | Done (part 3A-4) | Reset links are 32 random bytes, stored only as a SHA-256 hash in their own table, valid for 30 minutes and once. They go only to active customers. The link is checked before any hashing, and every refused link gets the same 400. A reset sets the new password, marks the email verified, ends every session, lifts the login blocks for the owner and sends a "password changed" notice without a link (ADR 0010). | Staff reset (staff part). The website must post the token from the URL straight away and keep it out of its logs. A password change while signed in (part 3C-1) needs the current password, ends every session, cancels any waiting reset link and sends the same notice (ADR 0018). |
| Admin invitations | Done (part 3B-4) | Only a Super User can invite (`@SuperUserOnly()`). The Admin's account starts with a random password nobody knows. The invitation link works the same way as a reset link: 32 random bytes, stored only as a SHA-256 hash in its own table (`staff_invitations`), valid for 72 hours and once, claimed atomically, and checked before any hashing. Every refused link gets the same `400`. Accepting sets the Admin's own password (16 to 128 characters), marks the email verified, ends any sessions, and is audited with the Admin as the actor. The Super User never sees the token or the link. The Admin still cannot sign in until a developer sets up their MFA (ADR 0015). Since part 3B-5, a Super User can send a pending Admin a new link, and every older link then stops working, or remove the pending Admin (ADR 0016). | The admin console must post the token from the URL straight away and keep it out of its logs. |
| Managing Admins | Done (part 3B-5) | Super Users only (`@SuperUserOnly()`), and only Admin accounts: a Super User's ID gets `404`. Path IDs must be UUIDs (`400`). Disabling ends every session of the Admin at once. Only a disabled or pending Admin can be removed, so an active one must be disabled first (`409`). Each rule is part of the database write itself, so two requests at the same moment cannot both change something. Every change is audited in the same transaction, a removal with a snapshot of who it was. The list never contains the password hash or the MFA secret (ADR 0016). | Once orders or shipments record which Admin handled them, decide whether removing must become "disable for good". A second approver for destructive actions (ADR 0004) is still open. |
| MFA | Done for staff (parts 3B-2 and 3B-3) | Staff MFA (ADR 0013):<br>• TOTP from authenticator apps, our own implementation proven against the RFC test vectors;<br>• ±30 seconds of clock drift allowed;<br>• no code works twice (atomic);<br>• secrets encrypted with AES-256-GCM, bound to the user, under a separate `MFA_ENCRYPTION_KEY`;<br>• set up only with `pnpm api:setup-staff-mfa`, which saves only after a valid code, ends all sessions and is audited.<br>Staff sign in only with the password and a current code together, checked in that order, with one answer for every failure (ADR 0014). A staff member without MFA cannot sign in at all. | Later: recovery codes (hashed), passkeys and a QR code in the admin console. Customers: password only for now (the owner's choice); optional MFA later. |
| Server-side permission enforcement | Done (customers and the two staff levels) | The server sets the role at registration and at an invitation, and zod drops unknown fields such as `role`. A global deny-by-default guard checks the token and the session on every request, and reads the user's current role from the database in the same query, never from the token. Customer routes take only `customer` tokens of active Customers. Routes marked `@StaffOnly()` take only `staff` tokens of active Admins and Super Users with MFA set up, and a token for the other audience is refused like a forged one (ADR 0014). Routes marked `@SuperUserOnly()` refuse Admins with `403`, through a global roles guard that fails closed (ADR 0015). Today these are all the Admin routes (inviting, listing, disabling and enabling, removing and inviting again, ADR 0016) and deleting a category, a product or a pack size. Admins create, change, activate and deactivate categories, products and pack sizes, and set prices, as the permission matrix proposes; only deleting is narrowed to Super Users, on that one handler (ADR 0020 to ADR 0022). The one exception, by the owner's choice: Admins delete product images too, because replacing a photo is everyday work, and the audit log records who deleted which (ADR 0023). Admins and Super Users alike receive stock, correct batches and change stock, as the matrix proposes ("adjust, view movements"). Nobody deletes stock: a mistake is put right with a correction, and a pack size or product that still holds stock cannot be deleted (ADR 0024). The matrix's approval of large price changes is not built: every price change is audited instead (ADR 0022). Since part 9, Admins and Super Users see every order and take it through packed, shipped and delivered. Only Super Users see payments and refunds, and cancel an order, because a paid order's payment then goes back: the refunds route is Super User only, and so is the cancel handler on its own (ADR 0028). | With the admin console features: finer staff permissions from the permission matrix in `docs/requirements.md`, once the owner has confirmed it. `staff/staff-routes.spec.ts` lists exactly which staff controllers, and which category, product, pack-size and order handlers, are Super User only, and names the image exception in its own test, so a change to that list is always deliberate. |
| Row-level security (RLS) | Decision: not now | The app connects as the database user that Docker creates, which is a superuser and bypasses RLS anyway. | Before production: separate database roles for migrations and for the running app (data access only, no schema changes). Ownership checks in the app stay the main control. RLS is optional later for orders, addresses and invoices. |

## 6. Must be done before the API leaves localhost

Rate limiting, brute-force protection and the hashing cap were on this list and were done in part 3D. Still open:

1. HTTPS everywhere, so HSTS takes effect, and TLS to the database.
2. The reverse proxy or load balancer listed in `TRUST_PROXY`. Without it, every customer would share the proxy's IP in the rate limits.
3. Separate database roles for migrations and for the running app. The app's role may only insert and read `audit_log`, so not even a compromised API can rewrite history or drop the triggers.
4. Secrets in a secret manager, one set per environment.
5. `/health/ready` details hidden from the public.
6. A log retention period. (The cleanup of expired sessions and tokens has run since part 3A-5.)
7. `pnpm audit` clean, Dependabot alerts on, secret scanning in CI, Docker images pinned by digest.
8. Encrypted backups with a rehearsed restore.
9. Image files from object storage behind a CDN, over HTTPS, with `MEDIA_BASE_URL` pointing at it. On a laptop the API serves `/media` itself, before the rate-limit guard (ADR 0023).
10. Razorpay live keys after the business's KYC, a new webhook secret for production, and Razorpay's webhook pointed at the deployed API's HTTPS address (ADR 0027).
11. The admin console on the same origin as the API, over HTTPS, with `ADMIN_ORIGIN` set to it (the session cookie then gets `Secure`), the headers of `apps/admin/src/security-headers.ts` sent by the host (`frame-ancestors` works only as a header), `index.html` never cached, and the build's `ADMIN_MEDIA_BASE_URL` set to the CDN's image address (ADR 0031).

- Change a control's status in the same pull request that changes the control.

## 8. Glossary

| Term | Meaning |
|---|---|
| ASVS | OWASP Application Security Verification Standard, the security checklist this project follows (Level 2). |
| argon2id | A slow, memory-hard password hashing algorithm recommended by OWASP. |
| BOLA | Broken object level authorization: reading or changing someone else's data by changing an ID in a request. |
| CGNAT | Carrier-grade NAT: a mobile or broadband provider puts many customers behind one public IP address. |
| Clickjacking | Showing a page inside another website's invisible frame, so a click meant for that website lands on the hidden page. `frame-ancestors 'none'` and `X-Frame-Options: DENY` forbid the framing. |
| CORP | Cross-Origin-Resource-Policy: a header that says which other websites may show a file, such as an image. helmet's default is "only this site"; `/media` allows every site. |
| CORS | Cross-origin resource sharing: the browser rules for which other websites may read the API's responses. |
| CSP | Content Security Policy: a header that tells the browser which scripts and resources a page may load. |
| CSRF | Cross-site request forgery: another website making the user's browser send a request that carries the user's cookies. |
| Decompression bomb | A small file that claims, or unpacks to, a huge image, made to fill the server's memory. Refused by reading the size from the header before decoding. |
| DPDP Act | India's Digital Personal Data Protection Act, 2023. |
| EXIF | Details a camera stores inside a photo, such as the date, the camera model and often the GPS location. Re-encoding drops them. |
| HKDF | A standard way to derive a separate key for one job from an existing secret. |
| HMAC | A signature made with a shared secret. Used to prove that a webhook really came from the payment gateway, and to hash rate-limit keys. |
| HttpOnly | A cookie flag that keeps the cookie away from the page's scripts: the browser still sends it, but no script can read it. |
| HSTS | A header that tells browsers to use HTTPS only. |
| JWT | JSON Web Token: the signed access token the app sends with each request. |
| Magic bytes | The fixed first bytes of a file format, such as `FF D8 FF` for JPEG. They say what a file really is, whatever its name or `Content-Type` claim. |
| MFA / TOTP | Multi-factor authentication. TOTP is the 6-digit code from an authenticator app. |
| RLS | Row-level security: PostgreSQL rules that limit which rows a database user can see. |
| SameSite=Strict | A cookie flag: the browser sends the cookie only on requests that start on the same site, never on one started from another website. |
| SSRF | Server-side request forgery: tricking the server into fetching a URL the attacker chooses. |
| Trusted Types | A browser feature, switched on by the Content Security Policy, that refuses any plain string written into HTML or turned into script, which stops most DOM-based XSS. |
| XSS | Cross-site scripting: getting the browser to run an attacker's script inside our website. |
